# Что Olive берёт из iiko — полный перечень

Документ для переноса загрузки данных из iiko в другой сервис. Здесь всё, что
база Olive (nutri-baza) сейчас получает из iiko: какие запросы, какие поля,
как они обрабатываются и во что превращаются. Состояние на 09.11.2026.

Код-источник: `myapp/iiko_sync.py`, функция `sync_products_from_iiko`.
Подробнее по отдельным темам:
- `docs/cost-export.md` — себестоимость (OLAP-отчёт) в деталях;
- `docs/erp-iiko-direct.md` — чистка состава, словарь ингредиентов, риски.

---

## 1. Коротко

У iiko **два разных API**, Olive использует оба:

| | **iikoCloud API** | **iiko Server API** |
|---|---|---|
| Адрес | `https://api-ru.iiko.services` | `IIKO_SERVER_URL` (вида `https://<сервер>.iiko.it/resto`) |
| Авторизация | `apiLogin` + `appId` + `clientSecret` → Bearer-токен | логин/пароль → токен в параметре `?key=` |
| Что даёт | список блюд (внешнее меню), названия, артикулы, категории, вес порции, КБЖУ на 100 г, фото | «название в системе», масса нетто, техкарты → **состав**, OLAP-отчёт → **себестоимость** |

Всего за одну синхронизацию — 7 видов запросов:

| № | Запрос | API | Что получаем |
|---|---|---|---|
| 1 | `POST /api/v2/access_token` | Cloud | токен |
| 2 | `POST /api/2/menu/by_id` | Cloud | **все блюда** внешнего меню: имя, артикул, категория, вес, КБЖУ, фото |
| 3 | `POST /api/1/nomenclature` | Cloud | запасные артикулы и названия (слабый фолбэк) |
| 4 | `GET /api/auth` | Server | токен (в конце обязательно `GET /api/auth/logout`) |
| 5 | `GET /api/v2/entities/products/list` | Server | карточки продуктов: название в системе, масса нетто, справочник сырья для состава |
| 6 | `GET /api/v2/assemblyCharts/getTree` | Server | техкарта **каждого** блюда (≈300 запросов, в 8 потоков) → состав |
| 7 | `POST /api/v2/reports/olap` | Server | себестоимость из расходных накладных за 60 дней |
| + | `GET <url фото>` | — | файл фото блюда по ссылке из меню |

Синхронизация запускается **вручную** кнопкой на сайте (`/iiko/sync/`),
по расписанию не идёт. Сейчас в базе 327 блюд.

## 2. Доступы

8 переменных (значения лежат в `~/nutri-baza/.env` на сервере Olive,
в этот файл их не переносить):

```
IIKO_CLOUD_API_KEY    # apiLogin из iikoWeb
IIKO_APP_ID           # приложение в кабинете разработчика iiko
IIKO_CLIENT_SECRET    # оттуда же
IIKO_ORG_ID           # UUID организации
IIKO_EXTERNAL_MENU_ID # id внешнего меню — в нём живут блюда Olive
IIKO_SERVER_URL       # адрес iiko Server
IIKO_SERVER_LOGIN     # пользователь iiko Server
IIKO_SERVER_PASSWORD
```

Для нового сервиса лучше завести **свои** `apiLogin`/`appId` и отдельного
пользователя iiko Server (только чтение): отзыв ключа одной системы не уронит
другую, в логах iiko видно, кто ходил, а лимиты Cloud API считаются на ключ.

## 3. Запросы подробно

### 3.1. Cloud: токен

```
POST https://api-ru.iiko.services/api/v2/access_token
{"apiLogin": "...", "appId": "...", "clientSecret": "..."}
→ {"token": "..."}
```
Дальше заголовок `Authorization: Bearer <token>`.
Старый `POST /api/1/access_token` (только `apiLogin`) iiko отключает —
в Olive он остался лишь запасным вариантом.

### 3.2. Cloud: внешнее меню — основной список блюд

```
POST /api/2/menu/by_id
{
  "externalMenuId": "<IIKO_EXTERNAL_MENU_ID>",
  "organizationIds": ["<IIKO_ORG_ID>"],
  "priceCategoryId": "00000000-0000-0000-0000-000000000000",
  "version": 2
}
```

Ответ: дерево `itemCategories[]` → `childCategories[]` (рекурсивно) →
`items[]`. Если `itemCategories` пуст — фолбэк на `productCategories[].items[]`.

Что берём из каждого `item` (размер — первый из `item.itemSizes[]`):

| Что | Откуда | Примечание |
|---|---|---|
| GUID блюда | `item.itemId` (или `item.id`) | главный ключ, совпадает с `id` карточки в iiko Server |
| Название из меню | `item.name` | запасное; основное имя — из iiko Server (3.5) |
| Артикул | `item.sku` → `size.sku` → `item.code` → `size.code` | первое непустое |
| Категория | `name` категории, в которой лежит блюдо | блюдо бывает в нескольких категориях — копим все |
| Ед. измерения / фасовка | `item.measureUnit` | |
| Вес порции, г | `size.portionWeightGrams` | запасной; основной — масса нетто из iiko Server (3.5) |
| КБЖУ на 100 г | `size.nutritionPerHundredGrams` (объект или список) → иначе `size.nutritions[0]` | поля `energy`, `proteins`, `fats`, `carbs` |
| Фото | `size.buttonImageUrl` → `item.buttonImageUrl` | ссылка, файл скачиваем отдельно |

### 3.3. Cloud: номенклатура (слабый фолбэк)

```
POST /api/1/nomenclature
{"organizationId": "<IIKO_ORG_ID>", "startRevision": 0}
```
Из `products[]`: `id`, `num` (или `code`) → артикул, `name` → название.
Покрывает только меню доставки (~85 позиций) и почти не пересекается
с внешним меню по GUID. Нужен только когда у блюда нет артикула в меню.
Новому сервису можно не повторять.

### 3.4. Server: токен

```
GET {IIKO_SERVER_URL}/api/auth?login=<логин>&pass=<пароль>
→ строка-токен (может быть в кавычках — снять)
```
Дальше во всех запросах параметр `?key=<токен>`.
**В конце обязательно** `GET /api/auth/logout?key=<токен>`, даже при ошибке —
иначе iiko Server исчерпает лицензионные сессии.

### 3.5. Server: карточки продуктов

```
GET /api/v2/entities/products/list?key=...&includeDeleted=false
→ [ {id, num, name, unitWeight, description, ...}, ... ]
```
Отдаёт **все** продукты сервера: и блюда, и сырьё, и полуфабрикаты. Берём:

| Что | Поле | Примечание |
|---|---|---|
| Название в системе | `name` | **приоритетнее** имени из меню: в меню имена правят руками и копируют (все поке там «с лососем») |
| Масса нетто | `unitWeight` | в **кг**; ×1000 → граммы, округление до целого, половина вверх. Приоритетнее веса порции из меню (там бывает вес с тарой: 380 г в меню при 320 г по карточке) |
| Описание | `description` | фолбэк для состава, если нет техкарты (бывает JSON-строкой со списком блоков `{text}`) |
| Справочник `id → name` | все продукты | нужен, чтобы назвать сырьё в техкартах |

Связь с блюдом меню: по GUID (`item.itemId == product.id`). Если не нашлось —
по артикулу (`sku` меню == `num` карточки), но **только если артикул уникален
с обеих сторон**: в Server бывают задвоенные `num`.

### 3.6. Server: техкарты → состав

Для каждого блюда меню, у которого есть карточка в Server:
```
GET /api/v2/assemblyCharts/getTree?key=...&date=<сегодня YYYY-MM-DD>&productId=<GUID блюда>
→ {"assemblyCharts": [ {assembledProductId, dateFrom, dateTo, items:[{productId, amountOut|amountMiddle|amountIn}]}, ... ]}
```
Пустой ответ = техкарты нет → берём `description` из карточки.

Именно `getTree`, а **не** `getPrepared`: `getPrepared` не заходит внутрь
полуфабрикатов со списанием DIRECT и теряет их ингредиенты.

Как собирается строка состава:
1. На один продукт бывает несколько карт (разные периоды) — берём действующую
   (`dateTo = null`), иначе с самой поздней `dateFrom`.
2. Рекурсивно раскрываем дерево от блюда; лист = продукт без своей карты
   (конечное сырьё). Количество перемножается по пути (`amountOut`, иначе
   `amountMiddle`, иначе `amountIn`).
3. Название сырья — по справочнику из 3.5.
4. Выкидываем упаковку (имя начинается с `У*`) и «Смесь газ».
5. Срезаем префикс вида `С* `, `П* `, `Б* `, `ПП* ` (1–3 заглавные буквы + `*`).
6. Одинаковое сырьё суммируем, сортируем по убыванию количества (основной
   ингредиент первым), склеиваем через `", "`.

Результат хранится как есть (`composition`). Отдельно Olive прогоняет его через
словарь ингредиентов (`myapp/ingredient_aliases.py`) — это уже логика Olive,
не данные iiko (см. раздел 5 и `docs/erp-iiko-direct.md`, раздел 5).

Запросов ≈ по одному на блюдо (~300), Olive шлёт их пулом из 8 потоков —
последовательно не укладывается в таймаут веб-сервера.

### 3.7. Server: OLAP-отчёт → себестоимость

```
POST /api/v2/reports/olap?key=...
Accept: application/json
{
  "reportType": "TRANSACTIONS",
  "groupByRowFields": ["DateTime.DateTyped", "Product.Id", "Product.Num", "Product.Name"],
  "groupByColFields": [],
  "aggregateFields": ["Sum.Incoming", "Amount.Out"],
  "filters": {
    "DateTime.OperDayFilter": {
      "filterType": "DateRange",
      "from": "<сегодня − 60 дней>T00:00:00",
      "to":   "<сегодня + 2 дня>T00:00:00",
      "includeLow": true, "includeHigh": false, "periodType": "CUSTOM"
    },
    "Product.ThirdParent": {"filterType": "IncludeValues", "values": ["ЗДОРОВОЕ ПИТАНИЕ"]},
    "TransactionType":     {"filterType": "IncludeValues", "values": ["OUTGOING_INVOICE"]}
  }
}
→ {"data": [ {"DateTime.DateTyped", "Product.Id", "Product.Num", "Product.Name", "Sum.Incoming", "Amount.Out"}, ... ]}
```

Обработка:
- себестоимость единицы = `Sum.Incoming / Amount.Out`;
- строки с нулевым количеством **или нулевой суммой** пропускаем — так iiko
  помечает списание с нулевого остатка (производство ещё не проведено);
- из нескольких дней по одному блюду берём **самый свежий**;
- поиск для блюда: по GUID (`Product.Id`), затем по артикулу (`Product.Num`).
  По названию **не ищем** — разные блюда в меню бывают с одинаковым именем;
- округление до 2 знаков.

Почему так: окно 60 дней — потому что в начале месяца у трети блюд в
накладных нулевая цена; `+2 дня` — накладные выписывают на завтрашний
учётный день. Подробно — `docs/cost-export.md`.

### 3.8. Фото

Скачивается по ссылке из меню (`buttonImageUrl`), обычный `GET` без авторизации.
Перекачивается, только если ссылка изменилась (в имени файла Olive хранит
md5-хэш ссылки).

## 4. Итог: поле Olive ← источник в iiko

| Поле в Olive (`Product`) | Источник | Обработка |
|---|---|---|
| `iiko_id` | меню: `item.itemId` | GUID блюда, ключ |
| `iiko_sku` | номенклатура Cloud: `num` по GUID, иначе сам GUID | технический ключ |
| `article` | меню: `sku`/`code`; если пусто — номенклатура `num` | артикул (код блюда) |
| `name` | Server: `name` карточки; фолбэк — меню `item.name` | |
| `iiko_category` | меню: имя категории | первая категория, совпавшая с картой категорий (раздел 6), иначе первая попавшаяся |
| `meal_categories` | меню: имя категории → карта категорий | ключ категории сайта (`breakfast`, `salad`, … `extra`) |
| `packing` | меню: `item.measureUnit` | |
| `net_weight` | Server: `unitWeight` (кг); фолбэк — меню `portionWeightGrams` (г) | хранится в **кг**, округление до целого грамма |
| `kcal_per_100`, `protein`, `fat`, `carbs` | меню: `energy`, `proteins`, `fats`, `carbs` на 100 г | как есть |
| `kj_per_100` | — | **вычисляется**: ккал × 4.184 |
| `*_per_serving` (ккал, Б, Ж, У, кДж) | — | **вычисляется**: значение на 100 г × масса нетто / 100, 2 знака |
| `composition` | Server: техкарта `getTree`; фолбэк — `description` | см. 3.6 |
| `cost` (себестоимость ФЗ) | Server: OLAP-отчёт | см. 3.7 |
| `photo` | меню: `buttonImageUrl` | файл скачивается |
| `iiko_synced_at` | — | время синхронизации |

## 5. Что считает сам Olive (в iiko этого нет)

Это не нужно забирать из iiko — это логика Olive поверх данных:

- **Цена продажи** (`sale_price`) = себестоимость × (1 + наценка), вверх до
  целого тенге. Наценка: **67%** на блюда (включая смузи), **15%** на напитки
  категории «Доп. товары». Можно задать вручную — тогда не пересчитывается.
- **Наценка в ₸ и %** — из себестоимости и цены продажи.
- **Чистый состав** (`composition_clean`) — состав из iiko через словарь
  ингредиентов (убирает артикульные хвосты, дубли, приводит названия).
- **Аллергены** — в базе Olive есть поле, но из iiko сейчас **не** загружаются.
- Рационы, группы, замены, калоражи, нормы КБЖУ — данные Olive.

## 6. Категории: iiko → сайт

Блюдо относится к категории сайта по **имени категории во внешнем меню**.
Сравнение нечувствительно к регистру, разным тире и слову «ккал».
Сопоставление редактируется в админке Olive (`IikoCategoryMap`); текущее:

| Категория в iiko (внешнее меню) | Ключ сайта |
|---|---|
| ПП* ЗАВТРАК | `breakfast` — Завтрак |
| ПП* ГОРЯЧЕЕ 400-500 ккал | `hot_400` — Горячее 400–500 |
| ПП* ГОРЯЧЕЕ 500-600 ккал | `hot_500` — Горячее 500–600 |
| ПП* СУП | `soup` — Суп |
| ПП* САЛАТ | `salad` — Салат |
| ПП* ВЫПЕЧКА/ДЕСЕРТ | `dessert` — Выпечка/Десерт |
| ПП* СМУЗИ | `smoothie` — Смузи |
| ПП* СЭНДВИЧИ | `sandwich` — Сэндвичи |
| ЖКТ (желудочно кишечный тракт) | `jkt` — ЖКТ |
| ПП* Доп. товары | `extra` — Доп. товары (напитки: Боржоми, EXPONENTA) |

Плюс старые названия на случай переименования в iiko: «Завтрак 250–350 ккал»,
«Второе 400–500 ккал», «Суп 200 ккал», «Салат 150–250 ккал», «Смузи 100–150 ккал»,
«Сэндвич 300–350 ккал» и короткие «Завтрак», «Горячее 400-500», «Суп», «Салат» и т.п.

Распределение сейчас: горячее 400–500 — 62, салат — 59, завтрак — 53,
ЖКТ — 38, горячее 500–600 — 36, суп — 21, смузи — 18, десерт — 17,
доп. товары — 13, сэндвичи — 10.

## 7. Сопоставление с уже существующими записями

Если новый сервис хранит свою базу и обновляет её, порядок поиска блюда:
1. по **артикулу** — устойчиво, даже если блюдо в iiko пересоздали
  (новый GUID, тот же артикул). Только артикулы, уникальные и в меню, и в базе;
2. по `iiko_sku`, затем по GUID (`iiko_id`).

Обновлять запись только если что-то реально изменилось; числа сравнивать
с округлением до 2 знаков (иначе «0.320» ≠ «0.32» и всё помечается изменённым).

Блюда, пропавшие из меню, Olive **не удаляет** (раньше авто-удаление стирало
блюда из рационов при пересоздании подгрупп в iiko) — только пишет в лог.

## 8. Грабли

- **logout в iiko Server обязателен**, иначе кончаются сессии.
- **429 / 503** от iiko — повтор с паузой 5, 10, 15 с (3 попытки).
- **Имя из меню ненадёжно** — брать «название в системе» из iiko Server.
- **Вес из меню ненадёжен** — брать `unitWeight` карточки (кг!).
- **Артикулы задваиваются** в iiko Server — сопоставлять по артикулу только уникальные.
- **Себестоимость = 0** в накладной — не цена, а отсутствие производства; пропускать.
- **getPrepared теряет состав** полуфабрикатов — только `getTree`.
- **Состав без техкарты** — фолбэк на `description` (может быть JSON-строкой).
